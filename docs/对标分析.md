# 对标分析：开源项目 → 本系统重构依据（2026-09-02）

> 结论先行：本系统最大的架构差距在「提取引擎」——开源标杆 invoice2data 用的是
> 可插拔文本来源 + 模板优先级联 + AI 兜底的流水线，而我们是写死的二选一。
> 其次是字典管理、数据留痕、报表中心三类 ERP 惯例。以下为逐项对比与改造决定。

## 一、逐项对比

### 1. 提取架构（对标 invoice2data，差距最大）

| invoice2data 的做法 | 我们现状 | 改造决定 |
|---|---|---|
| 文本来源可插拔：pdfium / pdftotext / pdfminer / pdfplumber / OCR 级联，一个失败自动换下一个 | parsers.py 已按格式分派（接近），但无级联 | 保留现有 parsers，补：PDF 无文字层时自动走 OCR 的级联（阶段一后补） |
| **模板优先**：每类固定格式文档配一个模板（关键词匹配 issuer + 每字段多条正则 + 静态字段），命中即秒提、免费、结果确定 | 无模板层；固定格式日报每次都烧 LLM，慢且花钱 | **新建模板提取器 + 模板管理页**：关键词匹配 → 字段正则提取 → 命中直接入库 |
| AI 只是兜底，且可反向用 AI 生成模板 | LLM 是唯一智能提取方式 | 级联顺序：模板 → LLM（未配置或失败降级规则）→ 规则 |
| 每字段允许多条正则、静态字段、行项目插件 | 规则提取只认关键词+金额 | 模板字段同样支持多条正则，输出统一结构 |

### 2. 字典管理（对标 money-pos / 华夏ERP）

| 他们的做法 | 我们现状 | 改造决定 |
|---|---|---|
| 系统管理里有「字典管理」：分类/枚举统一维护 | 分类是随手填的字符串，统计口径易乱 | 新建 dict_items 字典表（分类/支付方式/账户），管理页维护；LLM 提取的分类从字典里选；统计按字典聚合 |

### 3. 数据留痕与手工凭证（对标 ERP 惯例）

| 他们的做法 | 我们现状 | 改造决定 |
|---|---|---|
| 单据可追溯、修改有痕迹 | 记录改了就改了 | 手工记账 + record_edits 留痕表（谁、何时、原值→新值） |

### 4. 报表与指标（对标 POS 报表共识 + money-pos 首页报表）

| 他们的做法 | 我们现状 | 改造决定 |
|---|---|---|
| 笔数、客单价、支付方式占比是看板标配 | 只提取金额 | FinanceRecord 增加 tx_count、payments 字段；提取 schema 扩展；看板/报表中心展示 |
| 报表中心集中（日结单、分类排行、对比、导出） | 报表散落 | 新建报表中心页 + Excel 导出 |
| 环比/同比箭头、图表下钻联动 | 无 | 看板重构时实现 |

### 5. 权限（对标华夏ERP 按钮级权限）

华夏ERP 权限粒度到按钮和菜单。我们三角色已够用，本轮**不做**按钮级权限码（用户已确认），仅保留三角色 + 审计日志。

## 二、重构后的提取数据流

```
上传文件 → parsers（txt/csv/docx/xlsx/pdf/OCR → 纯文本）
        → 提取流水线 extractors.pipeline：
             ① 模板提取器（DB 中的模板，命中 → 产出，source=template）
             ② LLM 提取器（已配置则调用，source=llm，失败降级）
             ③ 规则提取器（关键词+表格映射兜底，source=rule）
        → 归一化（日期/金额/字典校验）→ finance_records（含 source/tx_count/payments）
```
